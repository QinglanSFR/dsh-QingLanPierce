# prompts/examples —— 密度与口气的标尺

这几份文件从主稿里拆出来，目的只有一个：**别让示例正文和表达细则跟硬规则挤在同一条注意力通道里**。quick-line.md / long-line.md 是从 qinglan-core.md 抽出来的；表达规则.md 是后加的独立层。

## 文件

| 文件 | 覆盖档位 | 内容 |
|---|---|---|
| `quick-line.md` | 快线 / 标准线 | 分诊口径、追问格式、交付顺序、密度标尺、完整示范、反例对照 |
| `long-line.md` | 长线 | 三个开工前置、推进纪律、STATE.md 模板、分批检查点、完整示范、反例对照 |
| `表达规则.md` | 全档 | 句法、口气、禁用表达、免疫条款、正误对照总表、口语化管理（第 7 节）、五问自检 |

## 怎么用

- **回答任何任务之前先读**（三档主稿的 `<examples>` 节都有硬性指针，指向这三份）。
- 它们是**标尺**，不是台词：照着密度和顺序写，内容按当前问题重新组织。
- 读到了不要在回答里提「我读过示例」。
- 读不到（路径不存在 / 无读权限）→ 按 persona 照常交付，并在结论末尾标一行「示例文件未读到」。

## 为什么拆出来

抽取前实测：

```
qinglan-core.md   10,486 字符 / 408 行
  persona         5,306 字符（50.6%）
    其中示例一、示例二   ~570 字符
  标题 33 个 / 离散指令 90 条
```

示例正文属于「输出长什么样」的参照，不属于「必须怎么做」的规则。放在同一条通道里，模型分不清哪句是硬约束、哪句是味道，容易做成规则平均。

拆出来后：

- 硬规则集中在文件前 100 行（禁止清单 → 三档判据）
- 叙事段（十年攒下的直觉 / 两个毛病）后置到 persona 尾部
- 示例按需加载，不常驻注意力通道

## 维护

- 改示例只改这两个文件，不动 `qinglan-core.md`。
- 新增档位或新增判据时，先改主稿，再同步这两份的对照表。
- 主稿里的 `{{EXAMPLES_DIR}}` 由 `index.js` 的 `buildSectionText()` 在运行时替换成本机绝对路径，**不要手工写死路径**。
